# Software & Data Security: Concepts, Simulation Steps, Pros/Cons, Applications

Companion to `security_simulator.html`. Each module lists the animated steps, pros, cons and real deployments.

## 1. Software Environment

Software lives in layers (apps, OS user mode, kernel mode, hardware+TPM) and talks to clients and the cloud. Three lifecycle views add risk: design (smallest threat surface), runtime (largest), and post-retirement (old versions still exposed).

**Working principle (simulation steps)**

1. An application asks for a service through the API (user mode).
2. The call crosses the gate into kernel mode; the Security Monitor checks permissions.
3. Approved requests go through memory/process managers and drivers to the HAL, which translates to the CPU instruction set.
4. Hardware executes; the TPM supplies a root of trust (keys, boot integrity measurements).
5. Results sync to the cloud over the internet, which widens the threat surface.

**Pros**
- Layer separation isolates faults
- HAL enables virtualization and portability
- TPM gives hardware-rooted trust

**Cons**
- Every layer is attack surface
- Kernel bugs are catastrophic
- Cloud links add remote exposure

**Applications / deployments**
- Commercial: Windows/Linux servers with TPM BitLocker
- Defense: hardened OS with secure boot
- Medical: special-purpose OS in pacemakers
- Industrial: embedded OS in PLCs

## 2. Malware Lifecycle

Malware types: virus (needs host), worm (self-spreads), Trojan (deceives), ransomware, logic bomb (trigger), dropper, keylogger, spyware, boot-sector virus, zombie/botnet.

**Working principle (simulation steps)**

1. Attacker delivers a lure: email attachment, fake game or macro document.
2. User clicks or opens it (social engineering); a virus attaches to a host file, a Trojan hides inside useful software.
3. A dropper installs further code and a backdoor; worms spread over the network by vulnerabilities.
4. Host becomes a zombie and joins a botnet awaiting commands.
5. Trigger fires (date/action) and payload runs: ransomware encrypts, keylogger steals, DDoS starts.

**Pros**
- Understanding stages lets you break the chain at each step
- Known strains have signatures

**Cons**
- Authors constantly change code to evade
- APT-weaponized ransomware is organized and persistent

**Applications / deployments**
- Seen in: WannaCry, SQL Slammer, ILOVEYOU, Melissa, Michelangelo
- Used defensively by red teams to emulate threats (MITRE ATT&CK)

## 3. Rootkits

A rootkit hides malicious presence to keep privileged access. Types: persistent, memory-based, user-mode, kernel-mode.

**Working principle (simulation steps)**

1. A tool lists files or processes using FindFirstFile or Task Manager.
2. User-mode rootkit hooks the call (DLL modification) and intercepts it.
3. The call continues to the Native API; advanced rootkits also hook this to defeat API-vs-Native comparisons.
4. Kernel-mode rootkits alter the SSDT or use DKOM to unlink their process from kernel structures.
5. The returned list omits the malware, so the tool shows a clean system.

**Pros**
- Studying them improves detection design
- Rebuild from clean media guarantees removal

**Cons**
- Hard to detect and remove
- Kernel level runs with admin-equal power; detectors can be fooled
- Persistent ones survive reboot

**Applications / deployments**
- Defense: offline scans, TPM-measured boot, IDS signatures
- Threat research: memory forensics
- Seen: Mebroot MBR rootkit (2007)

## 4. Web & Database Attacks

Fourteen database attack patterns include aggregation/inference, bypass, view compromise, alternative routes, contamination, deadlock, DoS, improper modification, interception, query (SQL injection), physical access, TOCTOU, web-based, unauthorized access. OWASP lists XSS, CSRF, injection, broken authentication, IDOR.

**Working principle (simulation steps)**

1. Attacker submits a malformed input (SQL injection / XSS) to the web app.
2. App builds a dynamic query without validation and sends it to the query engine.
3. Query bypasses the view restrictions; aggregation of harmless rows can infer sensitive data.
4. Alternative route: direct DB or file access skips the controls, or TOCTOU changes data after approval.
5. Poor architecture (DB placed in the DMZ) lets the web app breach expose customer data.

**Pros**
- Views give field-level control
- Parameterized queries, input validation and least privilege block most attacks

**Cons**
- Views limit seen data, not operations
- Multiple access routes are hard to secure
- Deadlocks or table scans cause DoS

**Applications / deployments**
- Commercial: e-commerce, payment systems (PCI DSS)
- Defense/gov: classified DB with labels
- Banking: web banking WAFs

## 5. Social Engineering & Recon

Phishing, smishing, vishing, spear phishing, whaling, scareware, plus low-tech recon: dumpster diving, shoulder surfing, Googling, media and social media intel.

**Working principle (simulation steps)**

1. Attacker gathers lingo, contacts and partners from websites, news, social media, dumpsters.
2. Builds a convincing message: phishing (mass), spear phishing (targeted), whaling (executives).
3. Victim is pressured to act: click, reveal a password, or pay a fake invoice.
4. Attacker collects the data or money and may pivot deeper.

**Pros**
- Awareness programs create a human firewall cheaply
- Microtraining is just-in-time

**Cons**
- Humans can still be fooled
- Hard to measure effectiveness

**Applications / deployments**
- Corporate: phishing simulations
- Banks: KYC and call-back verification
- Defense: OPSEC training

## 6. Detection & All-Source Intelligence

Inputs (IT/OT logs, UEBA, HUMINT) go through SIEM analytics and become a product: recommendations to leadership. Behavior blocking and sandboxes complement antivirus.

**Working principle (simulation steps)**

1. Logs, process measurements and sensors stream in from every system.
2. UEBA profiles every user, process and device; outliers are flagged.
3. Human sources (tickets, HR, threat blogs) add context, with privacy law care.
4. SIEM correlates events across time to spot APT precursors.
5. Analyst reports meaning plus recommendation; leadership acts.

**Pros**
- Spots unknown and insider threats
- Context reduces false alarms

**Cons**
- Needs skilled staff and tuning
- Privacy and labor-law limits
- Anomaly detection needs a good baseline

**Applications / deployments**
- Commercial: SOC with Splunk/Sentinel
- Defense: threat-intel fusion centers
- Critical infrastructure: OT monitoring

## 7. Countermeasures

Defense in depth: training, hardening, patching, isolation (VLAN, microsegmentation), DLP, antimalware, sandbox, CSIRT.

**Working principle (simulation steps)**

1. Train users (human firewall).
2. Disable unneeded services, patch on time to shrink the attack window.
3. Isolate critical and legacy systems to stop lateral movement.
4. DLP governs data sharing; antimalware blocks known and anomalous code.
5. Suspicious samples are run in a sandbox to learn behavior and make signatures.
6. CSIRT contains, eradicates and recovers, then feeds lessons back.

**Pros**
- Layers cover each other's gaps
- Sandboxes reveal C&C and behavior safely

**Cons**
- Cost and complexity
- Signature AV needs fresh updates
- Malware can detect sandboxes

**Applications / deployments**
- Commercial: PCI DSS-mandated antimalware
- Defense: network segmentation, CERTs
- Healthcare/energy: protect availability against DoS

## 8. Software Types & Mobile Code

Four categories: operating systems (general or special purpose, bound to CPU via HAL), utility programs, application programs, and mobile code / executable content (scripts, macros, applets that travel from server to client).

**Working principle (simulation steps)**

1. The OS abstracts CPU, network and storage; the HAL lets it run on different instruction sets and enables virtualization.
2. Utilities run stand-alone in user mode for specific jobs, such as system management or format translation.
3. Applications (games, accounting, IAAA, antimalware) use OS services and need the most security attention.
4. The web page downloads with embedded script; it executes on the client as the page renders.
5. Every app has a boundary and threat surface; an APT-style attacker probes it for easy entry.

**Pros**
- Clear categories guide control choices
- Mobile code gives rich web features

**Cons**
- Mobile code runs on the client unexpectedly
- Large threat surface at every boundary

**Applications / deployments**
- Commercial: Windows/Android/iOS
- Medical: special-purpose OS in pacemakers
- Mobile: apps, wearables, browser plug-ins

## 9. Secure Development & Protection Approaches

Secure software flows from requirements, specs, design, testing and security assessment to user procedures. Six approaches reduce risk: process, behavior, safety, standards/compliance, quality/integrity, availability.

**Working principle (simulation steps)**

1. Start with purpose plus functional and nonfunctional requirements.
2. Flow down into detailed system specifications.
3. Design software, systems and workflows. Errors here are cheapest to fix and easiest to control.
4. Test quality and assess security before release; rapid updates trade speed for safety.
5. Create end-user procedures and training.
6. At runtime the threat surface is largest; apply the six approaches, then retire old versions that may still be vulnerable.

**Pros**
- Early fixes cost less
- Multiple viewpoints expose different gaps

**Cons**
- Schedule pressure skips testing
- Overlapping versions stay exposed for years

**Applications / deployments**
- Commercial: SDLC, DevSecOps
- Safety: medical, energy, process control
- Compliance: PCI DSS audits

## 10. OWASP Web Vulnerabilities

Injection, XSS, CSRF, broken authentication and IDOR exploit poorly built web apps that were rushed to market.

**Working principle (simulation steps)**

1. Injection: attacker input (SQL, LDAP, OS command) is run as a command by the backend.
2. XSS: a malicious script stored or reflected in a page runs in the victim browser.
3. CSRF: a forged request rides on the victim logged-in session.
4. Broken authentication: weak or exposed sessions let an attacker impersonate a user.
5. IDOR: changing an ID in a URL returns another user data because no access check exists.

**Pros**
- Documented, preventable, testable
- OWASP gives a shared checklist

**Cons**
- Still the cause of most breaches
- Fast release cycles skip testing

**Applications / deployments**
- Commercial: WAFs, penetration tests
- Banking and e-commerce
- Government portals

## 11. Database: Aggregation, Bypass, Views, Alternate Routes

Aggregation combines harmless data into sensitive data; inference extracts more than allowed. Bypass skips the front end; views can be attacked; alternative routes and TOCTOU defeat checks.

**Working principle (simulation steps)**

1. Aggregation: the user combines unclassified rows from separate sources into classified knowledge; inference follows.
2. Compromised view: the user modifies a view, or uses it to perform unrestricted operations on visible data.
3. Bypass attack: avoids the query engine and CLI front end.
4. Alternate route: direct query or file system access reaches the same data unprotected.
5. TOCTOU: data is changed between approval of the query and display of results.

**Pros**
- Field-level, content-based views are granular
- Labels and least privilege restrict access

**Cons**
- Hard to verify view processing
- Multiple routes to the same data

**Applications / deployments**
- Defense/government: multilevel secure DBs
- Healthcare records
- Financial data warehouses

## 12. Database: Deadlock, DoS, Contamination, Interception, Modification

Reliability and integrity attacks on databases and warehouses.

**Working principle (simulation steps)**

1. Deadlock: A holds table 1 and waits for table 2; B holds table 2 and waits for table 1.
2. Resolution: the system aborts the cheapest transaction to roll back and sends an error to the user.
3. DoS: a poor query or full table scan locks tables and starves authorized users.
4. Data contamination: malformed field, record or file input disrupts the system.
5. Interception of remote sessions, or improper (even accidental) modification, harms confidentiality and integrity.

**Pros**
- Lock managers keep consistency
- Input validation and TLS reduce harm

**Cons**
- Deadlocks are hard to recognize
- Rollback costs time

**Applications / deployments**
- Banking transaction systems
- Airline reservations
- Hospital records

## 13. Four Windows Rootkit Types

Persistent, memory-based, user-mode and kernel-mode rootkits.

**Working principle (simulation steps)**

1. Persistent: code is stored in the registry or file system and runs every boot or login.
2. Memory-based: no persistent code, so a reboot removes it.
3. User-mode: hooks system calls in each application memory space (FindFirstFile/FindNextFile).
4. Kernel-mode: hooks the user-to-kernel gate (interrupt or MSR), edits the SSDT, or unlinks processes via DKOM.

**Pros**
- Know what to hunt for
- Kernel hooks are reliable for researchers too

**Cons**
- Detectors share the same privilege level
- Rebuild needed

**Applications / deployments**
- EDR and forensics
- Secure boot with TPM

## 14. Insider Threat, DoS & APT

Insiders exfiltrate data; DoS attacks threaten availability in hospitals, FAA towers and nuclear cooling; zombies amplify DoS; APTs use OWASP flaws and unknown vulnerabilities.

**Working principle (simulation steps)**

1. A disgruntled or compromised insider uses valid privileges to copy huge volumes of data.
2. Without continuous monitoring, the breach is discovered only after damage is done.
3. An APT patiently recons and exploits known or zero-day vulnerabilities.
4. Zombies flood the target in a DDoS, giving immediate disruption.
5. Hospitals, FAA towers or nuclear cooling lose availability, with possible loss of life.

**Pros**
- ML anomaly detection catches insiders
- Prioritizing availability protects safety

**Cons**
- Insiders look legitimate
- Monitoring raises privacy issues

**Applications / deployments**
- Defense: counter-insider programs
- Healthcare, aviation, energy
- Commercial: DDoS scrubbing

## 15. Media Threats & Due Diligence

Press coverage and social media reveal targets; the same sources support KYC and pre-employment screening.

**Working principle (simulation steps)**

1. News of contracts, facilities or problems draws attention.
2. Employee posts leak details or sentiment.
3. The actor profiles the organization and its people, then targets it.
4. Defender uses the same sources for KYC and screening of clients and hires.

**Pros**
- Cheap, open-source vetting
- Reduces hiring risk

**Cons**
- Cannot control media or staff posts
- Privacy limits

**Applications / deployments**
- Banks: KYC
- HR background checks
- Defense: OPSEC reviews

## 16. Antimalware, Behavior Blocking & Sandbox

Signature and anomaly antivirus, behavior blockers, spyware tools, sandboxes and interactive behavioral testing.

**Working principle (simulation steps)**

1. The file is scanned against signatures and anomaly models (needs fresh signatures).
2. A behavior blocker watches file, disk, startup and network actions in real time, blocking even obfuscated code.
3. Limitation: it must run first, so some harm may occur.
4. Sandbox: run in isolation to observe behavior and C&C, though some malware detects it.
5. Interactive testing: redirect via HOSTS to a lab server and interact with the malware.

**Pros**
- Behavior blocking defeats obfuscation
- Sandbox yields signatures

**Cons**
- Signatures lag new malware
- Anomaly models need baselines
- Sandbox evasion

**Applications / deployments**
- Enterprise endpoint suites
- Vendor labs (CWSandbox)
- PCI DSS compliance

## 17. CSIRT & Preparation

Prepare, detect and respond. CSIRT offers reactive, proactive and security-quality services; hardening can follow risk-based sensitivity.

**Working principle (simulation steps)**

1. Build the CSIRT, procedures and microtraining before an incident.
2. Detect precursors and indicators.
3. Contain spread and eradicate malware.
4. Recover systems.
5. Share lessons and tighten hardening based on risk.

**Pros**
- Faster response
- Shared community knowledge

**Cons**
- Costly to staff
- Needs authority

**Applications / deployments**
- Corporate SOCs
- National CERTs (CERT/CC)
- Product PSIRTs

## 18. ATM & POS Attacks

Shoulder surfing and swiping capture PINs and card data.

**Working principle (simulation steps)**

1. Camera or an onlooker records the PIN.
2. Fake reader or RFID scanner reads the card data.
3. Attacker combines both into a clone and withdraws cash.

**Pros**
- Awareness helps
- Chip and PIN reduce cloning

**Cons**
- Hard to inspect devices

**Applications / deployments**
- Banks: tamper checks
- Retail POS
